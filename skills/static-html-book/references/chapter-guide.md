# 章の書き方

## 章の型

```text
## この章で分かること
- 箇条書きで3〜4項目。読み終えたときにできるようになることを書く

## （本文の見出し）
問題 → 考え方 → 図 → 具体例（コード・設定）→ 落とし穴、の順で進める

## まとめ
- 箇条書きで3〜5項目。「この章で分かること」と対応させる

## 確認問題
1. 理解を確かめる問い
2. 実務で迷いそうな場面の問い

:::details 解答
1. ……
2. ……
:::
```

`check.py --strict` は、「この章で分かること」と「まとめ」の見出しと、図が1枚以上あることを検査する。

## レベルの合わせ方

- 想定する読者を「経験の長さ」と「この分野の知識」に分けて決める。たとえば「開発・運用の経験はあるが、AWS は初級〜中級」
- 読者がすでに知っていること（プログラミング、Git、HTTP など）は説明しない。この分野に固有の言葉は、初出で一言説明する
- 抽象的な説明のあとには、必ず具体例を置く。サンプルのコードは、読者の業務で出てきそうな題材にする
- 「なぜそうするのか」を書く。設定値だけを並べない。ありがちな失敗と、その避け方も書く

## 日本語の書き方

公式ドキュメントの日本語版は機械翻訳のことが多い。訳語をそのまま使わず、自然な日本語に直す。

| 避ける | 使う |
| --- | --- |
| 〜することができます | 〜できます |
| リソースをプロビジョニングします | リソースを作ります |
| 〜を有効化することが推奨されます | 〜を有効にしましょう |
| 〜に対するアクセス許可を付与します | 〜を使えるようにします |
| 〜という形になります | 〜です |

- 一文一義にする。1つの文に2つ以上の主張を入れない
- 主語と述語を近づける。長い修飾語は文を分けて後ろに回す
- サービス名・API 名・設定項目名は、英語の正式名をそのまま書く（`kms:Sign`、`RemovalPolicy` など）
- 文末は「です・ます」でそろえる

## 事実の確かめ方

- 仕様・上限値・既定値は、公式ドキュメントの英語版で確かめる
- 料金・提供状況（新規受付の停止など）は変わりやすい。確認した時期を本文に書き、公式の料金ページなどを確かめるよう促す
- サンプルで使う値は架空のものにする。AWS なら、アカウント ID は `111122223333`、ドメインは `example.com` を使う
