# ストーリー設計

デッキの良し悪しは本文を書く前のストーリーで決まる。deck.json の `story` ブロック（purpose / audience / desired_action / key_message）が根幹で、スライドはその展開にすぎない。

## 受入基準（通常モード）

起案は任せるが、以下をすべて満たすこと:

- **主張は1文**: 各コンテンツスライドの message は「〜する」「〜である」と言い切る主張文。テーマ名（「移行方針」など）をタイトルにしない
- **見出しだけで話が通る**: message を上から順に読むだけで、結論→根拠→手順→対処の流れが追える
- **反論への備え**: 聴衆が突っ込みそうな点（費用・リスク・他案）への回答がスライドに含まれる
- **枚数範囲**: ブリーフに指定がなければ10〜20枚。増えたら削るか2部構成を提案する
- **構造部品は骨格だけ**: 表紙・目次・区切り・まとめはストーリーを運ぶための器。まとめ（closing）は「承認してほしい事項」など欲しい行動に直結させる

## 穴埋めフォーム（厳密モード／Luna）

厳密モードでは以下を**全項目**埋めてから deck.json に進む。空欄や「不明」があれば本人に聞く。

```
purpose        : （このデッキで得たい結果。例: 予算の承認）
audience       : （決裁者・参加者。例: 情シス部長・業務部門代表）
desired_action : （読後に取ってほしい行動を動詞で。例: 日程と要員の承認）
key_message    : （デッキ全体の主張を1文で）
枚数上限       : （例: 15枚以内）
前提・数値     : （使う数字とその出所。想定値は「想定値」と明記）
```

各スライドについて:

```
component : （決定表から1つ。下表）
message   : （主張1文。構造部品は null）
slots     : （componentの定義に合わせた中身）
notes     : （話し手メモ1〜3文。構造部品は空でもよい）
```

### 内容の型 → component の選び方

表紙・目次・区切り・まとめはテンプレの構造部品を使う。内容スライドは、template-map.json に対応する部品があればそれを優先する。map に無い図解は `references/components.md` のライブラリから、情報の関係（比較・順序・階層・定量など）に合わせて選ぶ。テンプレとライブラリの両方に同じ名前がある場合もテンプレが優先される。

部品のvariant・slot・件数上限は [components.md](components.md) を参照する。適切な図解が選べず、複数の候補で伝わり方が大きく変わる場合は本人に確認する。テンプレ独自の意匠が必要なら、SKILL.md「テンプレに部品が無いとき」に従って見本部品を追加する。

### deck.json の修正上限

スキーマ検証・build のエラーは最大3回まで修正を試みる。4回目が必要になったら止めて、エラー内容と試した修正を報告する。

## 話し手メモ（notes）

- スライドの本文をなぞるのではなく、口で補う説明・根拠・前置きを書く（1〜3文）
- 想定値・未確定の数字は「想定値」と明記する
- 組織テンプレの見本スライドにノート欄の指示がある場合（map の `notes_instructions`）はそれに従う
