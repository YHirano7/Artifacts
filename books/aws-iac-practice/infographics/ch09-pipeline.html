マージされたコードだけが、差分確認と承認を経て本番に届く
4章の「変更セットで確かめてから反映する」手順を、CodePipeline の5つのステージにしたものです
1 SOURCE
変更を取得
CodeCommit
  • main への push で起動
  • レビュー済みのコードだけ
→
2 BUILD
テストとsynth
CodeBuild
  • go test・Lambdaビルド
  • tsc・npm test・cdk synth
1つでも失敗したら停止
→
3 PREPARE
変更セット作成
CodeBuild
  • --method=
    prepare-change-set
  • まだ何も変わらない
→
4 APPROVE
人が承認
Manual Approval
  • Replacement の有無を確認
  • 鍵・台帳の置き換えは差し戻す
→
5 DEPLOY
変更セット実行
CloudFormation
  • ① KmsStack
  • ② CertIssuerStack
依存の順に1つずつ
権限はブートストラップのロールに寄せる
deploy-role変更セットの作成（CodeBuild が引き受ける）
file-publishing-roleLambda のコードなどの資材をアップロード
cfn-exec-roleCloudFormation が実際にリソースを変更
CodeBuild 自身には sts:AssumeRole だけを与えます
パイプライン自身は手で更新する
このサンプルは自己更新（self-mutation）をしません。
PipelineStack は初回も変更時も、管理者が cdk deploy で反映します。パイプラインが自分の権限を広げる変更を、承認なしで通さないためです。
成果物も暗号化する
アーティファクト用の S3 バケットは、7章の DataKey で暗号化し、公開アクセスをブロック、SSL 必須にします。
テンプレートやビルド結果も、設定情報を含む大事なデータです。
GitHubを使うならSource ステージを AWS CodeConnections に差し替えるだけで、Build 以降はそのまま使えます
