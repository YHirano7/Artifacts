スタックは「変わる速さ」で分け、依存は一方向にする
よく変わる層は何度作り直しても困らないように、データと鍵の層は削除から厚く守ります
層サンプルでの例と注意点変更頻度
デリバリー他を更新する
CodePipeline・CodeBuildPipelineStack
他のスタックを更新する権限を持つので、変更は慎重に
低い
アプリ作り直せる
Lambda・API GatewayCertIssuerStack
頻繁に変わる。物理名を固定せず、置換されても困らない形に
高い
↑ 上の層が下の層を参照する（逆向きの参照は作らない）
データ消えると戻らない
DynamoDB・S3CertIssuerStack
RemovalPolicy.RETAIN とバックアップ（PITR・バージョニング）
低い
基盤影響が最大
KMS の鍵・VPCKmsStack
鍵を消すと、暗号化したデータがすべて読めなくなる
低い
運用で効く5つの備え
1
削除と置換から守るDeletionPolicy・UpdateReplacePolicy・終了保護
2
論理 ID を変えないConstruct の id 変更は作り直しになる
3
ドリフトを検出するdetect-stack-drift で手作業の変更を見つける
4
シークレットは書かないSecrets Manager の動的参照で渡す
5
コストを見える化するタグで配分し、鍵やCAの月額を把握する
原則変更は変更セットで差分を確かめ、人が承認してから反映する（9章のパイプライン）
